Liskov Substitution Principle (LSP) — *Severity: High* > *"Objects of a superclass should be replaceable with objects of a subclass without affecting the correctness of the program."* #### 1. Inconsistent Halt and Termination Contracts When a plugin decides to block or short-circuit a request, the mechanism is inconsistent across plugins: - **`IPRestrictionPlugin` / `PromptGuardPlugin`:** Mutate `pctx.Stop = true`, `pctx.StopStatusCode = 400`, `pctx.StopErrorBody = []byte(...)`, and return `nil`. - **`SemanticCachePlugin`:** Directly calls `pctx.ResponseWriter.WriteHeader(200)` and `pctx.ResponseWriter.Write(cachedData)`, sets `pctx.Stop = true`, and returns `nil`. - **General Error Handling:** Other plugins might return a non-nil `error` from `Exec*`, which causes `PluginEngine` to immediately return that error. If a caller substitutes one blocking plugin for another, the side effects on `http.ResponseWriter` and the gateway flow are radically different and unpredictable. #### 2. `AsyncPostUpstreamPlugin` Behavioral Fracture ([plugin.go](file:///data/per-pro/llm-gateway/internal/plugin/plugin.go#L74-L79), [engine.go](file:///data/per-pro/llm-gateway/internal/plugin/engine.go#L368-L384)) ```go type AsyncPostUpstreamPlugin interface { IsAsyncPostUpstream() bool } ``` `PluginEngine.RunPostUpstream` inspects whether the plugin implements `AsyncPostUpstreamPlugin`: - If `true`: It executes `targetPlugin.ExecPostUpstream` inside a background goroutine, **completely ignores any returned error** (`_ = ...`), and returns immediately. - If `false`: It executes synchronously in-line and aborts on error. This violates LSP because implementing this interface breaks the contract of `PostUpstreamPlugin`: 1. The caller cannot rely on execution guarantees or error propagation. 2. Any mutations to `pctx` inside an async plugin are silently discarded. 3. **Data Race Danger:** The engine creates a shallow copy `pctxCopy := *pctx`. However, pointers (`pctxCopy.ExtraHeaders`, `pctxCopy.CanReq`, `pctxCopy.ResponseWriter`) point to the **same underlying memory** as the main request goroutine. If an async plugin reads/writes `ExtraHeaders` or `CanReq` while `gateway.go` is serializing the response, Go's race detector triggers data race errors. --- ## 3. Each interceptor decides whether to modify the request, halt execution cleanly via a standard `ExecutionResult`, or delegate to `next()`. ### Pattern 2: Role-Based Interface Segregation (ISP Solution) Segregate `PluginContext` into phase-specific, read-only interfaces paired with narrow action controllers: - Plugins never receive database pointers or transport writer objects. ### Pattern 3: Dependency Inversion via Interfaces & Constructor Injection (DIP Solution) Extract storage requirements into focused domain interfaces: - `RateLimiter`: `Allow(ctx, key string, limit int) (bool, error)` - `CacheStore`: `Get(ctx, key string) ([]byte, bool, error)` and `Set(ctx, key string, val []byte, ttl time.Duration) error` - `CostCalculator`: `GetSpent(ctx, tenantID, keyID uuid.UUID) (float64, error)` Inject these interfaces into the plugin structs when registering them in the registry: `NewRateLimitingPlugin(limiter RateLimiter)` ### Pattern 4: Observer / Event-Driven Architecture (Observability Plugins) Separate **mutating plugins** (which alter requests/responses) from **observability plugins** (metrics, logging, traces, webhooks). - Observability plugins should not be interceptors. They are **Observers** that subscribe to `RequestCompletedEvent`. - An in-memory or worker-pool `EventBus` broadcasts events asynchronously without hacking marker interfaces (`IsAsyncPostUpstream`) or risking data races on shared request pointers. --- ## 5.
